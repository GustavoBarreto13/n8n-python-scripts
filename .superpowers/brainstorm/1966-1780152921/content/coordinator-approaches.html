Como implementar o coordenador único

3 abordagens — escolha baseada em complexidade vs. poder

A

Script stateless (mais simples)

n8n chama coordinator/agent.py --query "..." via spawnSync.
ADK roda, responde, termina. Sem memória entre mensagens.

✅ Zero infra nova
✅ Fit perfeito com n8n
✅ Fácil debugar
⚠️ Sem memória
⚠️ "quanto gastei?" sem contexto
⚠️ Cada msg é conversa nova
B

Serviço persistente no VPS (recomendado)

Coordinator roda como processo Python permanente no Docker.
n8n chama via HTTP. Mantém sessão por usuário do Telegram.

✅ Memória entre mensagens
✅ "continue o que falamos" funciona
✅ Ainda no seu VPS
⚠️ Precisa de container novo
⚠️ Gerenciar uptime/restart
⚠️ Um pouco mais complexo
C

Vertex AI Agent Engine (Google Cloud)

Deploy do coordinator no Google Cloud.
Google gerencia sessões, scaling e uptime. n8n chama via API.

✅ Managed, sem ops
✅ Sessões nativas
✅ Integração GCP (BigQuery etc.)
⚠️ Custo GCP por query
⚠️ Setup mais complexo
⚠️ Vendor lock-in Google

O que muda no Telegram com a opção B (recomendada)

HOJE — dois fluxos separados
Telegram → n8n → nami/main.py → Telegram
Schedule → lucy/main.py → Telegram
COM COORDENADOR — um ponto de entrada
Telegram → n8n → coordinator → Telegram
Schedule → lucy/main.py → Telegram (batch, não muda)
O digest diário (batch) continua rodando separado — não faz sentido passar pelo coordinator.
O coordinator é só para interações em tempo real iniciadas pelo usuário.
