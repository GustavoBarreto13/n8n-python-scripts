Multi-agente: um coordenador que controla Nami e Lucy

No ADK, agentes podem ser tools de outros agentes — nativamente

A hierarquia

🧠 Coordenador
recebe mensagens do Telegram
decide quem chamar e quando
🪙 Nami Agent
+ create_transaction()
+ query_expenses()
+ delete_transaction()
✉️ Lucy Agent
+ fetch_emails()
+ label_and_archive()
+ search_emails()
No ADK: coordinator = Agent(sub_agents=[nami_agent, lucy_agent]) — isso é tudo.

Pedidos que cruzam os dois agentes

"Olha esse email do Nubank e já lança a transação no Notion"
Lucy lê
→ Nami cria
Lucy.fetch_emails(from="nubank") →
Nami.create_transaction(valor=..., conta="Nu")
"Quanto gastei em delivery esse mês? E tem confirmação de pedido na caixa?"
paralelo
Nami.query_expenses(cat="delivery") +
Lucy.fetch_emails(keyword="pedido") → resposta unificada
"Resumo do meu dia: o que gastei e o que está pendente na caixa"
paralelo
→ síntese
Nami.query_expenses(today=True) +
Lucy.fetch_emails(action="responder") → síntese final

Como o ADK lida com isso — o código

# Cada agente é independente:
nami = Agent(name="nami", model="gemini-2.0-flash", tools=[create_tx, query_expenses])
lucy = Agent(name="lucy", model="gemini-2.0-flash", tools=[fetch_emails, archive])
# O coordenador usa os dois como sub-agentes:
coordinator = Agent(
name="coordinator",
model="gemini-2.0-flash",
sub_agents=[nami, lucy], # ← isso é tudo
instruction="Você gerencia finanças (Nami) e email (Lucy)..."
)
# Uso:
runner.run("lança 89 no Rappi e arquiva o email de confirmação")
# → coordinator decide → chama Nami + Lucy → resposta única
O que você ganha
  • Um único ponto de entrada no Telegram
  • Ações cross-agente sem código extra
  • Cada agente continua independente
  • Fácil adicionar um 3º agente depois
O que ainda precisa resolver
  • Sessão: onde fica o histórico? (InMemory ou Firestore)
  • Auth: cada agente tem suas próprias credenciais
  • Deploy: o ADK roda como processo Python — não substitui o n8n
  • Custo: queries cross-agente são mais caras
